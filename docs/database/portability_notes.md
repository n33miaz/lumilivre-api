# Portabilidade entre bancos — LumiLivre

> Versão: 2026-05-22.
> Audiência: arquitetos avaliando se o LumiLivre pode rodar fora do
> PostgreSQL.

**TL;DR:** PostgreSQL é dependência forte. Portar para MySQL, MariaDB ou
SQL Server é viável, mas você perde busca textual eficiente (`pg_trgm`),
materialized views nativas e tipos como `CITEXT`. O custo é refazer ~25 %
do schema + ~5 % do código de repositórios.

Veja [ADR-013](./ADR-013-postgresql-strong-dependency.md) para o
racional formal.

---

## 1. O que muda em cada banco

### 1.1 MySQL 8 / MariaDB 10.5+

| Recurso Postgres                          | Equivalente MySQL / MariaDB                                  | Custo da troca                          |
|-------------------------------------------|--------------------------------------------------------------|-----------------------------------------|
| `UUID` + `gen_random_uuid()`              | `CHAR(36)` + `UUID()` ou `BINARY(16)` + `UUID_TO_BIN`        | Médio: índices BINARY são mais rápidos. |
| `TIMESTAMPTZ`                             | `TIMESTAMP` (UTC) + coluna explícita `time_zone`             | Alto: aplicação precisa lidar com TZ.   |
| `CITEXT`                                  | Coluna `VARCHAR` + collation `utf8mb4_0900_ai_ci`            | Baixo.                                  |
| `gen_random_uuid()` (extensão)            | `UUID()` ou `uuid_v4()` em MariaDB 10.7+                     | Trivial.                                |
| `pg_trgm` GIN (busca rápida `ILIKE`)      | `FULLTEXT INDEX` (limitações: idiomas, tamanho mínimo)       | Alto: re-escrever queries de busca.     |
| `unaccent` + `immutable_unaccent`         | sem equivalente; substituir por collation `*_ai_ci`          | Médio.                                  |
| `MATERIALIZED VIEW`                       | Tabela + `EVENT` (cron) ou `CREATE TABLE ... AS SELECT` + job aplicacional | Alto: re-implementar `DashboardService.refreshViews()`. |
| `REFRESH MATERIALIZED VIEW CONCURRENTLY`  | sem equivalente direto                                       | Médio.                                  |
| `GENERATED BY DEFAULT AS IDENTITY`        | `INT AUTO_INCREMENT` ou `GENERATED ALWAYS AS IDENTITY` (10.7+) | Trivial.                              |
| `UNIQUE INDEX ... WHERE deleted_at IS NULL` (parcial) | sem suporte — usar trigger ou coluna calculada `is_active` + `UNIQUE` | Médio.        |
| `COUNT(*) FILTER (WHERE ...)`             | `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`                       | Baixo (verboso, mas direto).            |
| `WITH (FORMAT csv)` em `COPY`             | `LOAD DATA INFILE`                                           | Baixo.                                  |
| `array_agg` / `ARRAY[...]`                | `JSON_ARRAYAGG` / `JSON_TABLE`                               | Médio.                                  |

**Veredito MySQL/MariaDB:** factível mas trabalhoso. Estime ~5 dias de
engenharia para schema + ajustes em repositórios.

### 1.2 SQL Server 2019+

| Recurso Postgres                | Equivalente SQL Server                                | Custo da troca |
|---------------------------------|-------------------------------------------------------|----------------|
| `UUID`                          | `UNIQUEIDENTIFIER` + `NEWSEQUENTIALID()`              | Trivial.       |
| `TIMESTAMPTZ`                   | `DATETIMEOFFSET`                                      | Trivial.       |
| `CITEXT`                        | Collation `Latin1_General_CI_AS`                      | Trivial.       |
| `pg_trgm`                       | `LIKE` simples (sem GIN); `FULLTEXT INDEX` para busca | Médio.         |
| `MATERIALIZED VIEW`             | `INDEXED VIEW` (com restrições) ou tabela + Service Broker | Alto.   |
| Triggers `touch_updated_at`     | `CREATE TRIGGER FOR UPDATE`                           | Trivial.       |
| Soft-delete + UNIQUE parcial    | `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL` (suportado em SQL Server 2008+) | Trivial. |

**Veredito SQL Server:** mais próximo de Postgres do que MySQL.
~3 dias de engenharia.

### 1.3 SQLite (apenas para protótipos)

Não suporta `BOOLEAN` real, `TIMESTAMPTZ`, `CITEXT`, materialized views,
nem RLS. Útil só para tests rápidos isolados — não recomendado para
deploy.

## 2. O que **não** se perde ao portar

- Schema lógico das tabelas (FKs, CHECKs).
- Regras de negócio (ficam em Java, não em triggers).
- Outbox pattern, audit_log, jobs agendados.
- Migrations via Flyway — Flyway suporta MySQL, MariaDB, SQL Server.
- Cache Redis, JWT, integração SMTP — independentes do banco.

---

## 3. O que **sim** se perde ao portar (ou exige redesign)

| Recurso                                               | Impacto se descartado                                      |
|-------------------------------------------------------|------------------------------------------------------------|
| Busca trigram em `student.full_name`, `book.title` etc. | Busca `ILIKE` cai para O(n) sem índice. Aceitável < 50k.   |
| `unaccent` para queries `Á → A`                        | Buscas por "Joao" não acham "João" sem collation `_ai`.    |
| Materialized views `mv_dashboard_stats` etc.           | Dashboard precisa recalcular sob demanda ou agendar refresh manual.       |
| UNIQUE parcial em `book.isbn WHERE deleted_at IS NULL` | Não conseguirá reutilizar ISBN de livro deletado.          |
| CITEXT em e-mails                                       | Comparações de email exigem `LOWER()` explícito.           |
| Extensão `pgcrypto`                                     | Geração de UUID volta para `uuid_generate_v4()` ou app.    |

## 4. Como portar — receita resumida

1. **Defina o banco alvo** (recomendo MariaDB 10.11 se quiser ficar
   próximo do FOSS; SQL Server se quiser cobertura corporativa).
2. **Gere o schema alvo** a partir do `ddl_standalone.sql`, substituindo
   tipos e constraints conforme tabela acima.
3. **Atualize `application.properties`** com o driver JDBC do alvo
   (`com.mysql.cj.jdbc.Driver`, etc.).
4. **Atualize `pom.xml`** adicionando o driver e removendo `postgresql`.
5. **Refatore views materializadas** para tabelas + job:
   - Crie tabela `dashboard_stats` com mesma estrutura.
   - Substitua `DashboardService.refreshViews()` por SELECTs comuns
     persistindo na tabela.
6. **Refatore busca avançada** que usa `pg_trgm`:
   - Cobertura simples: trocar `ILIKE` por `LIKE` com collation
     case-insensitive.
   - Cobertura escalável: FULLTEXT index do banco alvo.
7. **Refatore triggers** `touch_updated_at` para a sintaxe equivalente.
8. **Refatore CHECK constraints** equivalentes
   (`CHECK (status IN (...))` é padrão SQL — funciona em todos).
9. **Reaplique testes**:
   - Mude `FlywayMigrationTest` para usar `MySQLContainer`/`MSSQLServerContainer`.
   - Rode `mvn verify` até verde.

## 6. Por que escolhemos PostgreSQL como dependência forte

Detalhado em [ADR-013](./ADR-013-postgresql-strong-dependency.md). Resumo:

- **Custo de troca alto não é arbitrário** — vem de aproveitar o melhor
  do Postgres (trigram, materialized views, citext, RLS).
- **Trade-off consciente**: priorizamos qualidade da busca, simplicidade
  do dashboard e segurança RLS sobre a portabilidade teórica.
- **Implementações alternativas são aceitáveis** se a equipe assumir
  os custos listados aqui.
